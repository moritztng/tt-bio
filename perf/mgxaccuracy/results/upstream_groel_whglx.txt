## WHY THIS ARM EXISTS

The row's verdict rests on GroEL: four n=8 cells, size costs +14.754 A at offset 0 and
+12.647 A at offset 560. The reference half rests entirely on 1GPB -- the target whose 2x2
this row REFUTED as one protein's personality. So the close, as it stood, refuted a target
and then used that same target as its only upstream comparison. The doc named this as a limit
of the close. It is now a measurement instead.

This does NOT change how the row closes. `plans/closing_rule.txt` §4 is pre-registered on the
qb2 1GPB pair and stays the deciding test. GroEL here is corroboration, read the same way the
banked 512 valid draw was read: m=1 orders nothing at 0.05, but a draw landing inside the
device's own range removes a direction.

## WHY whglx AND NOT qb2, WHICH THE BRIEF NAMES

The brief routes CPU references to qb2 "where there are idle cores". That premise expired.
Measured this pass:

    qb2     16 cores, load 66-70   -- oversubscribed 4x, carrying three non-MGX rows
    whglx   64 cores, load 10-20   -- ~45 cores idle, 402 GiB free

qb2's saturation is exactly why the two draws that gate this row are 8-12 h out: each gets
2.26 cores of the 6 it asked for. Putting a third draw there would slow the two that decide
the row. whglx's live app is served off its cards, not its CPUs, and the brief's own limit
there is to keep load low: this arm's two draws take ~15 of 64 cores, load 15 -> ~30.

## READING THE PROGRESS OF THESE RUNS: THE LAUNCHED PID IS NOT THE JOB

On whglx, `boltzgen run` forks a Lightning child and waits on it. `ps -o times` on the pid the
launcher started reads a frozen 61 s and `/proc/<pid>/wchan` reads `do_wait`, which looks
exactly like a wedge. The work is in the child:

    2229330  boltzgen (wrapper)   61 CPU-s, not moving, state Sl, wchan do_wait
      2241290  python (the job)   809 CPU-s in 197 s = 4.1 cores    <- this is the measurement

This is the third instrument trap in this row's CPU accounting, after `ps -o pcpu` being a
lifetime average (`results/upstream_pair_eta.txt` §1). Read the CHILD, differenced over >= 300 s.
qb2's draws do not have this shape -- there the tracked pid is itself the worker -- so the same
command means different things on the two hosts.

## COST AND EXPECTED LANDING

The 512 rung is 592 tokens and the 1536 rung is 1616, the same token counts as the 1GPB valid
draws, so the banked cost model applies unchanged: design cost scales as tokens^2 off the
5126.3 s / 6-thread 512 draw, and the 1536 job costs (195.5k, 229.2k] CPU-s. The lower bound
is an observation, not an assumption: qb2 draw a is still running at 195,500 CPU-s.

    rung   threads   occupancy (child)   expected wall     expected landing
     512         6   4.39 cores          1.66-1.95 h       ~19:33-19:51Z
    1536        16   7.68 cores          7.07-8.29 h       ~01:03-02:17Z

Both occupancies are measured, not assumed: cumulative child CPU over a 735 s (512) and 501 s
(1536) baseline. 16 threads buys 7.68 cores, not 16, so the thread count is worth about 1.75x the
6-thread rung rather than 2.7x.

One caveat on transferring the cost band: it was derived from a 1GPB draw and GroEL 1536 has three
chains where 1GPB has two. Token count is identical (1616) and cost is driven by tokens, so the
band should hold, but treat the landings as projections until the 512 rung actually lands and
gives this target its own anchor.
